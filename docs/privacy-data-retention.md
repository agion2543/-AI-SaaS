# 个人信息与数据保留策略（产品默认）

这份说明用于明确当前产品的默认保留口径和代码实际状态，不是法律意见，也不代表已经取得合规认证。商家、平台经营主体和部署环境可能承担不同义务；正式上线前应由专业人员结合业务关系、支付与财税要求、争议处理和部署地规则复核。

## 数据库备份的验证与保留策略

备份保留目标统一为“每日备份，滚动保留最近 30 天”。每次发布前的手动备份应计入该窗口；确需延长保留时，应由数据负责人另行明确批准并记录负责人、理由和到期日。备份脚本现支持 age 加密，另有手动清理工具；仍没有每日任务或自动清理。本地合成恢复演练不读取现有备份，不能替代生产恢复验证。

### 加密与密钥管理

备份依赖 [age 上游命令行工具](https://github.com/FiloSottile/age)及 `AGE_RECIPIENTS_FILE` 环境变量。该文件是公开 recipients 清单，可包含一条或多条 age 公钥；它不是解密密钥。生成 identity 时，将私钥保存在仓库、备份目录和普通部署包之外的受控位置，并另做离线/异地恢复副本；丢失所有对应 identity 后，密文无法恢复。私钥绝不可提交到 Git。换钥时可先把新公钥加入 recipients 清单；旧备份仍需旧 identity 解密，因此旧私钥应至少保留到相应备份过期。

```bash
# 一次性生成：把私钥文件放在仓库之外的受控位置；输出的 recipients 文件仅含公钥
age-keygen -o /secure/path/backup-identity.txt
age-keygen -y /secure/path/backup-identity.txt > /secure/path/backup-recipients.txt
chmod 600 /secure/path/backup-identity.txt

# 每次备份：AGE_RECIPIENTS_FILE 指向 recipients 公钥清单；BACKUP_DIR 必须是明确目录
AGE_RECIPIENTS_FILE=/secure/path/backup-recipients.txt BACKUP_DIR=/path/to/backups bash scripts/backup-mysql.sh
```

Windows PowerShell 同样通过 `AGE_RECIPIENTS_FILE` 指定公钥清单；数据库密码只从 `MYSQL_PWD` 进程环境变量读取，不提供 `-Password` 命令行参数，并会在调用 age 前清除 `MYSQL_PWD` 与 `DB_PASSWORD`，随后恢复调用者原值。Bash 版从 `DB_PASSWORD` 取得密码并为 `mysqldump` 设置 `MYSQL_PWD`；启动 age 时通过 `env -u` 同时移除这两个变量。备份目录应由管理员限制访问；临时明文文件的删除不是对 SSD、快照或日志介质的安全擦除保证。

### 合成测试与加密完整性清单

`bash scripts/test-backup-mysql.sh` 和 Windows PowerShell 测试用假的 `mysqldump` 与 age 程序检查加密调用、密码隔离、失败/空输出清理、私有临时文件及不覆盖行为；mock 输出不是实际密文。`bash scripts/test-backup-retention.sh` 只在临时目录测试默认 dry-run、确认令牌、候选变化、最后一份保护及符号链接拒绝。以上 mock 测试不证明真实 age 加解密或备份可恢复。

可运行以下命令执行独立的合成端到端恢复演练：

```bash
bash scripts/test-backup-restore-age.sh
```

它要求 Linux 非 root 环境已本地安装 `age`、`age-keygen`、MySQL 8.x 的 `mysqld`/`mysql`/`mysqladmin`、`ss`、`ps` 及常见 Linux 命令行工具；不联网、不下载、不安装。脚本用临时生成的密钥、mock `mysqldump` 与合成 SQL 调用 Bash 备份脚本，使用真实本地 age 加密/解密并逐字节比较，再导入新建的 TCP 关闭、仅 Unix socket 的临时 MySQL，核对精确合成行数和内容。它拒绝调用方环境中非空的 `MYSQL_DSN`、`MYSQL_PWD` 或 `DB_PASSWORD`，并清理本次创建的文件和进程；若不能安全停止 MySQL，则保留 datadir 并报告路径。该脚本仅验证合成路径，不读取任何现有/生产备份，不验证生产密钥保管、异地副本、生产恢复流程或 Windows PowerShell。

`scripts/backup-integrity.py` 提供显式指定目录的本地完整性清单与只读校验，支持 `.sql` 和 `.sql.age`，不设默认备份目录：

```bash
BACKUP_DIR="/path/to/backups" # 替换为实际备份目录
MANIFEST="/path/to/backup-manifests/backups-YYYY-MM-DD.json" # 替换为实际清单路径；父目录须已存在
python3 scripts/backup-integrity.py create --backup-dir "$BACKUP_DIR" --manifest "$MANIFEST"
python3 scripts/backup-integrity.py verify --backup-dir "$BACKUP_DIR" --manifest "$MANIFEST"
bash scripts/test-backup-integrity.sh
```

`create` 只读取该目录下直接放置的 `.sql` 或 `.sql.age` 常规文件，为每个文件记录文件名、字节数和 SHA-256，并以 0600 权限新建 JSON 清单；清单目标已存在时拒绝覆盖。`verify` 只读对照文件清单、大小和 SHA-256，并拒绝符号链接；新增、缺失、改名或内容变化都会失败。对 `.sql.age` 计算的是密文哈希，不会解密。清单建议保存在备份目录之外并妥善保护。该哈希清单不是签名，不能防止同时有权修改备份和清单的人重新计算哈希，也不证明 SQL 可恢复。测试只用临时目录与合成文件，不接触真实备份。

生产备份的恢复验证尚未完成。合成恢复脚本 `bash scripts/test-backup-restore-age.sh` 不访问已有备份；它只验证本地合成 SQL 的真实 age 加解密、字节比较和临时 MySQL 导入。完整性清单也未对任何现有真实备份运行；需由操作者明确指定目录及清单路径后才会读取所选 SQL 或密文文件计算哈希。`backup-retention.py` 的清理按文件修改时间（UTC）筛选直接位于指定目录的 `.sql.age` 文件，默认仅预览；应用时必须提供与当前候选集合、文件大小和时间戳绑定的确认令牌，候选变化会使令牌失效，并拒绝删除最后一份加密备份。它不递归、不删除明文 `.sql`，也不自动运行。任何生产备份恢复验证都必须使用明确隔离的目标环境，并记录 dump 标识、校验结果、恢复结果和时间；不得将生产数据库、客户数据或生产凭据用于本地测试。

## 清理启用与安全边界

对业务数据库中的验证码、审计和其他个人信息，当前没有定时清理器、启动钩子、请求中清理逻辑或实际删除命令。只读 dry-run 仍按验证码 `expires_at`、审计 `created_at` 计算候选数量，并按两类审计 3 年/2 年的规则分类。新增的备份清理工具只管理加密备份文件，不删除业务数据库记录。相关业务数据测试只在合成 SQLite 数据上运行，未连接真实数据库。

未来若要实施业务数据库记录删除，必须先让用户/数据负责人看到确切的筛选条件、候选记录数、时间范围、影响表和备份/恢复方案，再由其明确批准一次性执行；执行默认关闭，不能因部署或常规启动而启用。还需先定义人工暂停删除的争议/诉讼例外，以及执行失败、部分成功和恢复步骤。本仓库目前没有业务记录删除开关、确认流程或回滚方案；这与仅管理加密备份文件的手动保留工具不同，不得把产品保留目标误读为已启用的自动删除。

如未来获批执行，建议先为受影响表/数据库创建加密备份，记录备份标识与时间，并在隔离环境验证可恢复；删除本身没有“撤销”操作，回滚只能从执行前备份恢复，且可能覆盖备份之后的新写入。备份脚本现支持 age 加密，完整性工具支持密文哈希，清理工具需手动令牌确认；但真实密钥、生产备份及恢复流程尚未验证，不能据此认为已具备经过演练的回滚能力。

## 访问控制与展示

商家只能通过其租户范围内的单笔订单详情读取完整顾客电话；订单列表、财务列表和商家看板使用脱敏号码。公开门店页保留商家联系电话，不展示商家邮箱。客户线索需要电话以便商家跟进，因此保留当前线索看板实际使用的称呼、电话和状态；不把留言、跟进备注或门店/商家关联对象一并返回。公开提交线索的成功响应只返回提交成功状态，不回显顾客电话和留言。

新的审计事件使用 `actor_id`/`actor_type`、对象类型/ID、动作、创建时间及用途。审计记录不复制订单备注、顾客留言、电话、IP 或浏览器标识。审计保留目标与网络日志保留是两套规则，不应把 IP 放进客户访问审计来替代网络安全日志。

## 法律依据与适用边界

- 《个人信息保护法》第十九条要求，除法律、行政法规另有规定外，个人信息保存期限应为实现处理目的所必要的最短时间；第四十七条规定目的已实现、期限届满等情形下的删除义务：[国家网信办公布的法律全文](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)。如处理活动需要个人信息保护影响评估，相关评估报告和处理情况记录依法至少保存三年。
- 《电子商务法》第三十一条要求电子商务平台经营者保存平台商品/服务信息和交易信息，自交易完成之日起不少于三年：[商务部公布的法律全文](https://www.mofcom.gov.cn/zhrmghgdzswf/fg/art/2018/art_cc9187dd95cd40158552d78a610e8c29.html)。是否适用于本产品运营主体及某类交易，要结合实际平台角色判断，不能简单套用于所有商家数据。
- 修正后的《网络安全法》第二十三条要求网络运营者留存相关网络日志不少于六个月；修正决定自 2026 年 1 月 1 日起施行：[修正后全文](https://www.cac.gov.cn/2025-12/29/c_1768735112911946.htm)、[全国人大常委会修正决定](https://www.cac.gov.cn/2025-10/29/c_1763461514768457.htm)。

法律最低期限不等同于个人信息可以无限期保存。发生未结退款、投诉、诉讼、审计或其他法定留存义务时，应记录暂停删除的理由和结束条件；义务结束后重新评估并删除或匿名化非必要字段。
